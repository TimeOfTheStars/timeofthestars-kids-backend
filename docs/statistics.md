## Доктрина: ничего не хранится

Единственный источник истины — сырые данные: матчи, строки участия и голы. Таблица, очки,
бомбардиры, карьера игрока и общая статистика команды **считаются на лету** при каждом
запросе. Хранимых счётчиков нет, поэтому им нечему рассинхронизироваться.

Два исключения, и оба контролируемые:

1. `goals`/`assists` в строке протокола — производные, их перезаписывает сервер из
   таймлайна при каждом сохранении. Клиент прислать их не может.
2. Поправка к общей статистике команды — сознательно хранимая величина, см.
   [ниже](#общая-статистика-команды-и-поправка).

## Откуда берутся данные

Источник — бумажный «ПРОТОКОЛ ИГРЫ ПО ХОККЕЮ». Структура данных повторяет бланк:

| На бумаге | В данных |
|---|---|
| Шапка: формат игры, продолжительность периода | `gameFormat`, `periodMinutes`, `periodsCount` у турнира |
| «МАТЧ №» | `matchNo` (в кабинете `position`) |
| «ТАБЛО МАТЧА»: Броски, Голы | `shotsA/B`, `scoreA/B` у матча |
| «СОСТАВЫ КОМАНД»: № и ФИО, вратарь отдельной строкой | строки участия с `isGoalie`, номер из заявки на турнир |
| «ВЗЯТИЕ ВОРОТ»: № · ВРЕМЯ · Г(ГОЛ) · П(ПАС) | события таймлайна |

**Чего в бланке нет** и что поэтому не может быть точным в данных:

- **период гола** — на бумаге не печатается. Вводится вручную, у уже внесённых матчей
  «Летнего Кубка» проставлен первым. Не строьте логику, критично зависящую от разбивки
  по периодам;
- **абсолютное время** — только `MM:SS` внутри периода;
- **амплуа полевых игроков** — отмечены лишь вратари;
- **даты рождения** — их в протоколе нет вовсе.

## Голы и передачи

Считаются из таймлайна, а не вводятся:

- гол → +1 автору;
- каждый непустой ассистент → +1 передача. Передач бывает **0, 1 или 2** — на бланке
  в столбце П(ПАС) номера пишут через запятую;
- `points` = `goals + assists`;
- «Игры» = число строк участия. **Само наличие строки означает «этот игрок играл»**.

Тип события один — «гол». Буллитов, штрафов, голов в пустые ворота в схеме нет. Отсюда
полезное свойство: **сумма голов команды в таймлайне точно равна её счёту**, на этом можно
строить проверки. (В соседнем взрослом проекте это не так — там голы с буллитов расходились
со счётом.)

Порядок строк таймлайна задаёт `sort_order`, а не время: в бумажном протоколе времена
идут не по возрастанию (13:36, 12:36, 08:46, …), порядок определяет колонка «№».

## Вратарские показатели

**Производные от табло, а не измеренные.** В бланке броски и голы записываются по команде
целиком, отдельной строки на вратаря нет. Поэтому:

```
пропущено (goalsAgainst) = голы соперника
отражено  (saves)        = броски соперника − голы соперника
```

Следствия, которые надо учитывать на фронте:

- **`saves` равно `null`, если броски в табло не заполнены** — процент отражённых тогда
  посчитать нельзя, показывайте прочерк;
- **если у команды в матче отмечено двое вратарей**, распределить командные цифры между ними
  невозможно, и такой матч **не входит** в их `goalsAgainst`/`saves`. В `games` он при этом
  учтён — то есть у вратаря может быть 3 игры и цифры только за 2 из них. В кабинете такие
  матчи перечислены в `goalie_ambiguous_team_ids`;
- если **ни один** матч вратаря не удалось отнести (в каждом было двое вратарей), поля
  `goalsAgainst`, `saves` и `minutesPlayed` приходят `null` — «неизвестно». Ноль там не
  ставится: «ПШ 0, ОБ 0» читалось бы как сухие матчи.

**`minutesPlayed` — не фактическое время на льду.** Это `periodMinutes × periodsCount`,
начисленное в предположении, что вратарь отыграл матч целиком. Подписывать как «время
в воротах» корректно, как «сыграно минут» — нет. Регламент у турнира не заполнен — поле
придёт `null`.

Процент отражённых сервер не считает. Нужен — считайте `saves / (saves + goalsAgainst)`,
предварительно проверив, что `saves !== null`.

## Таблица турнира

- В зачёт идут **все** матчи с заполненным счётом. Стадий и плей-офф в схеме нет.
- Очки: победа 2, ничья 1, поражение 0.
- Порядок: `очки → разница шайб → забитые шайбы → название`. Сервер отдаёт отсортированным,
  `place` = индекс + 1.
- Заявленная, но не игравшая команда присутствует с нулями. При равных очках она окажется
  выше проигравшей с отрицательной разницей — это цепочка tie-break, а не ошибка.

## Общая статистика команды и поправка

Показатели команды за всю историю (`GET /teams`) считаются по заведённым матчам:

- `tournaments` — турниры, где есть **хотя бы один матч с заполненным счётом**. Заявка без
  матчей не считается;
- `games`, `wins`, `draws`, `losses`, `goalsFor`, `goalsAgainst` — по матчам;
- `points` — из побед и ничьих.

### Зачем поправка

Матчи старых турниров в систему могут быть ещё не внесены: из 10 турниров в базе матчи есть
у одного. Расчёт тогда покажет «3 игры» команде, реально проведшей десятки. Поэтому есть
ручная поправка.

### Как она работает

**Складывающая, а не замещающая модель:**

```
итог = расчёт по заведённым матчам + поправка
```

Хранится именно поправка, а не итог. Поэтому новые заведённые матчи **продолжают
прибавляться** к итогу автоматически, и цифра не устаревает.

Кабинет при этом работает в **итогах**: администратор вводит то число, которое хочет
видеть (`total_games: 23`), сервер вычитает свежий расчёт и сохраняет разницу. Пустое
значение убирает поправку. Итог, совпавший с расчётом, поправки не создаёт.

Пример: расчёт 3 игры, задан итог 23 → сохранено `+20`. Сыграли ещё матч → расчёт 4,
итог 24. Прежняя модель («перезапись итога») оставила бы 23, и цифру приходилось бы
править после каждого матча — от неё отказались именно поэтому.

Поправка может быть **отрицательной**: иначе итог нельзя было бы уменьшить.

### Ограничение, которого не избежать

Поправка не знает, какие именно матчи она покрывает. Когда матчи старого турнира заведут
задним числом, расчёт вырастет, а поправка останется — итог окажется завышен, и её нужно
будет уменьшить руками. Без хранения истории по каждому турниру этого не обойти ни в одной
модели.

Публичный API отдаёт только итог и **не раскрывает**, где есть поправка. Кабинету
доступны `computed`, `corrections` и `corrected_fields`.

## Подводные камни

### 1. `games` в разных ручках означает разное

- в `/tournaments/{id}/players`, `/players/{id}/stats`, `/teams` — число матчей;
- в составе внутри `/games/{id}` — всегда `1`, это статистика одного матча.

### 2. Порядок отдаёт сервер

`standings` и `best-players` приходят отсортированными, `games` — в порядке `matchNo`,
`goals` — в хронологическом порядке ввода, состав в `/games/{id}` — вратари первыми, дальше
по номеру. Пересортировка на фронте только всё испортит.

### 3. Числа могут не сходиться, если протокол заполнен наполовину

Табло и таймлайн вводятся в одной форме, но независимо. Кабинет подсвечивает расхождение,
однако сохранить такой протокол можно. Если для вас важно, что число голов совпадает
со счётом, — проверяйте это на фронте и деградируйте мягко. Поля
`goals_in_timeline_a/b` в кабинете существуют именно для такой сверки.

### 4. Статистика команды может быть больше суммы по её матчам

Это учтённая история, а не ошибка. `games` не обязан равняться `wins + draws + losses`,
если поправка задана лишь части полей. При этом `points` всегда согласованы с `wins`
и `draws` того же ответа: очки не задаются вручную.

Нужна заведомо только «системная» арифметика — считайте из `/tournaments/{id}/standings`
и `/tournaments/{id}/games`: там поправок нет.

### 5. Один игрок может быть заявлен за две команды одного турнира

Схема этого не запрещает. Тогда в `/tournaments/{id}/players` и `/best-players` он
появится **двумя строками** — по одной на команду, с раздельной статистикой. Математика
при этом верна (карьера складывается корректно), но список выглядит как дубль. Если
показываете списки — стоит предусмотреть такой случай.

### 6. Незаигравшие есть в одних списках и нет в других

`/tournaments/{id}/players` возвращает всю заявку, включая игроков с нулями.
`/best-players` их отбрасывает.
